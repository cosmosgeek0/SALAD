# Dashboard memory correction — 8 September 2026

The dashboard's decoded fleet-ledger cache caused excessive retained memory and large rebuild peaks. The corrected reader streams lines, caches compressed records, and decodes one record at a time. Its historical Honeygain source lookup also remains compressed until a referenced timestamp is needed. Only `dashboard/fleet_test.py` was installed, followed by one dashboard restart at **15:57:18 UTC**. The installed SHA-256 is `aac886edc4e36e875a268de190a372910bd40371bf80c297393a59b54195667a`.

## Evidence and attribution

The independently retrieved system and kernel journals confirm the **14:21:06 UTC** global OOM: dashboard PID 755559, UID 997, was killed, with 965,784 KiB anonymous RSS and a systemd-reported 1,006.1 MiB memory peak. It restarted at 14:21:12. This predates the Pawns historical acquisition and metadata writes; neither the requesting caller nor the exact allocation active at the kill is established. Other processes also consumed memory. The earlier Unix-socket backlog incident is separate.

At 15:45:31, the restarted dashboard held **747,044 KiB RSS (729.5 MiB)** with one thread. Its Python modules matched the checkout. The fleet ledger was about 141 MB, with 15,672 retained rows; the HG source ledger was about 24.5 MB. A bounded 128-row fleet sample occupied 3,230,186 bytes after decoding, implying about **377 MiB** for the retained raw fleet objects alone. That is an estimate from the sample, not a heap dump of the killed process. The old cold reader also held up to 128 MiB of file bytes plus a separate split-line copy while constructing decoded objects; it retained all decoded HG source records and a second worker lookup. Compact browser output did not avoid these allocations.

A separate **synthetic** 16,000-record, 150 MB ledger reproduced the expansion locally. Old/new full snapshots and all five history ranges had identical hashes. Peak process memory, including full-history output, fell from **906.2 to 499.1 MiB**. No full production ledger was loaded into another diagnostic process on the shared host. Production comparisons used bounded samples.

## Limits and rebuilding

This fixes the demonstrated decoded-memory expansion; it does not identify the caller at the original kill or guarantee arbitrary future load. Compressed history and full export results still consume memory. Rebuilding a snapshot reparses retained compressed records: the measured first cold public HG request took **10.0 seconds**, later rebuild requests took roughly **3.5–6.2 seconds**, and cached requests generally took **0.27–1.3 seconds**. Current all-history took 4.18 seconds; archived history/export took 0.34/0.38 seconds. These measurements use the unchanged production CPU setting. The existing HG source-map invalidation by mtime is unchanged.
